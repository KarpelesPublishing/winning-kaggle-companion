A beam that is too narrow returns a path that is not a solution

How does beam width change whether a legal flip path reaches the sorted order within five flips?

A search must return a legal path and a success flag, and the flag decides whether the path counts. Beam search keeps only a few states per depth, so a narrow beam can discard the states that lead to the goal. With a zero heuristic the beam is cut by tuple order, not by progress toward the goal.

With width 5 the search tried 4 x 20 = 80 flips over 20 expanded states. The path replays to 1 4 3 5 2, which is not sorted, so this is a failed completion; it is the first retained state by tuple order, not a best attempt. Separately, the reversed tuple (4, 3, 2, 1) has 4 misplaced positions but needs 1 flip, so the mismatch count overshoots the true cost by 4 - 1 = 3 and is not a lower bound.

Worked steps

  1. Beam width: at most 5 states kept per depth.
  2. Flips tried: 4 x 20 = 80.
  3. Returned path (prefix lengths): 5, 4, 3, 5, 3.
  4. Replaying the path ends at 1 4 3 5 2.
  5. Solved flag: 0, so the result is an explicit failure.

Use the idea

Replay every returned move against an independent validator and report an explicit incomplete status when the budget ends. Compare beam widths under a fixed expansion or runtime budget and never score an unsolved path.

Where the conclusion applies

Classic pancake sorting on one five-pancake start, with five depth expansions and a zero heuristic. This is not the Santa 2024 competition, and its rules are not verified here. Reaching the goal says nothing about optimality of a pruned beam, and one start state does not show how width behaves in general.
